# Composition and Density

Compose relationships before containers. The enemy is the interchangeable vertical stack. The overcorrection is compression that crowds every viewport.

- Full and bounded redesign → this process; tweak or new piece → inherits existing composition.
- Density = content relationships per viewport, not smaller text; a sparse direction still carries every required claim, mechanism, action, and state.

## Inventory before layout

- **Objects**: products, records, people, places, files, or events the interface is about.
- **Decisions**: what the audience must understand, compare, choose, or do.
- **Claims and evidence**: each promise beside its mechanism, proof, constraint, or example.
- **Actions and states**: primary and secondary actions; loading, empty, error, success, permission, and live states that can occur.
- **Subject artifacts**: real units, labels, documents, instruments, imagery, and vernacular from Phase 1.

Short ask for an admin, dashboard or tool screen → complete it with what a mature product carries; a literal reading builds an empty page:

- navigation that places the screen inside its product;
- search and filtering over every collection the screen shows;
- data visualisation of the figures the screen's job turns on;
- rich components chosen for this content's relationships, never a fixed kit;
- every reachable state of every region.

Only an admin, dashboard or tool screen always carries this minimum, whatever the Scope answer:

- navigation with an icon on each item;
- search;
- a user menu;
- stat counters, each with a sparkline;
- at least one chart;
- a table with avatars, status badges, sortable columns, and row checkboxes that open a bulk action bar;
- a detail panel.

- Any other screen (lesson, checkout, game, consumer app) = task screen: content comes from the user's tasks there.
- A task screen stays focused: no sidebar, stat counters or chart unless one of the user's tasks needs it; each competes with the task.

- Each completed item except the states → scope group in the inventory, so the scope form lists it.
- Each minimum item → its own fixed scope group, so the plan check lists it and fails a plan missing one.
- Ask naming no product → plain category name and generic content, never an invented brand or domain.
- Marketing page → communicates what the offer is, why credible, how it works or differs, what to do next. App view → owes the obligations of its surface class below.

## Name and substantiate the content

- Name things by what the person controls and recognizes, never by how the system is built: *notifications*, not *webhook configuration*.
- Describe what a thing does, not sell it: "Search across all 40 fields", not "Powerful search".
- Established brand vocabulary exists → use it. Otherwise → one register per flow; verbs, contractions, and formality consistent ("All clear. Nothing needs you." and "0 open incidents" belong to different flows).

- Marketing claim → at least one mechanism, constraint, example, or proof nearby; never fill sections by paraphrasing one benefit.
- App work → populate every named field with a normal value, each documented boundary, and a value triggering each represented error state.
- Values → from the repository or subject materials; invented values labeled as assumptions; never invent regulated, safety, customer, or performance claims.

## Turn subject evidence into a system

Write at least three Phase 1 observations as `evidence → structural or content behavior → recurring echo`: one changing composition or navigation, one changing how real content or data is presented; palette and type alone do not qualify. Form, not a style to copy: `repair chronology → time-anchored work surface → timestamps align filters and detail`.

These mappings = subject system: they shape structure and content, never a theme, metaphor or prop the user did not ask for.

## Choose structures from relationships

Cards → for objects reorderable or removable without changing a neighboring object's meaning.

- Do not put paragraphs forming one argument in separate cards.
- Do not repeat one card anatomy for three or more content types.

Each content cluster → name the relationship before choosing its container:

- sequence or causality → a narrative track, timeline, or staged reveal;
- comparison → aligned rows, a matrix, or synchronized panels;
- evidence attached to a claim → an annotation, proof rail, or shared figure;
- hierarchy → index/detail, anchored rail, or nested headings without nested cards;
- changing values → a table, plot, log, meter, or subject-specific instrument;
- filters acting on results → one workbench with controls visibly attached to the result field;
- a browsable collection → a list, rail, gallery, or map chosen for how its objects differ.

Interrupting task → container from the task's own shape, never habit:

- surrounding context must stay readable while the task runs → side panel; closing the context loses the reason for the edit;
- task short, self-contained, blocking everything until it resolves → modal; page behind it inert;
- task carries its own sections, more than roughly seven fields, or a step sequence → its own route; a scrolling modal forfeits URL, back button, and focus order;
- task is one value on one object → edit in place; a container around one field costs more attention than the field.

## Write a composition contract

Reject the contract if any holds:

- it is a uniform vertical stack;
- two consecutive regions repeat the same anatomy without a content reason;
- its labels can be replaced with “hero / features / cards / CTA” without losing meaning.

Before code, record all five:

1. Whole-page or whole-view desktop map, every region labeled by content job, not component name.
2. Mobile reading and action order: what combines, becomes sticky, scrolls intentionally, or moves behind disclosure.
3. One focal point, two secondary beats, and the three or more recurring subject mappings.
4. A density rhythm: name regions showing three or more peer items, regions holding more than two prose sentences, and the one focal region.
5. Path from arrival to the page's job, naming where evidence, mechanism, and primary action enter it.

## Build density without clutter

- Do not repeat one container anatomy and gap across three consecutive regions with different relationships.
- Texture, motion, and illustration cannot compensate for a missing proof, workflow, or decision.
- Each screenful advances at least two of context, evidence, mechanism, comparison, decision, action. Exception: focal opening may advance one when the next region appears in the same viewport or behind a labeled scroll cue.
- Whitespace → named job: grouping, separation, pause, or staging.
- Gap between related items ≤ gap separating their group from the next.
- Layer only related information: annotation over its artifact, controls beside results, proof beside claim. Decorative overlap is not density.

## Surface obligations

Each surface class owes content, hierarchy, interaction, and verification, never a visual preset:

- **Marketing**: opening thesis paired with a concrete artifact, mechanism, or proof; claims interleaved with evidence, not repeated benefit blocks; closing adds decision-relevant information, not only a larger CTA.
- **Application workspace**: expose current context; primary work surface before summaries (summary is that surface when the page's job is monitoring or overview); controls beside what they change; build the states that alter the next action. Verify: walk the primary task in the render.
- **Data-dense**: align units, changing figures tabular, sort and filter → result relationship visible.
- **Data-dense**: repository, workflow, or brief holds a comparison → make it the organizing act; holds exceptions → surface them, not bury them. Locate each in the render; invent neither to satisfy this list.
- **Editorial or immersive**: reading rhythm and pacing are the structure; scroll tied to real content progression; every staging job named. Verify reading order at both widths.

## Responsive recomposition

Mobile reduces simultaneity, not substance.

- Preserve every content obligation; explicit reading order; secondary tools behind labeled disclosure; primary action reachable at the decision point.
- Tables and plots → labeled scroll region, pinned key columns, changed comparison axis, or detail view; never page-level horizontal scroll.

Touch-first surface: thumb sweeps the lower half, strains for the top corners.

- Repeated primary action → lower band; a simply stacked desktop layout leaves it at the top, out of thumb reach.
- Rarely used and destructive actions → top corners, out of stray-thumb reach.
- Never place a frequent action and a destructive one adjacent in the same band.

## Pre-ship composition sweep

- [ ] Every content obligation from the inventory appears in the rendered design?
- [ ] Full or bounded redesign → three or more supporting subject mappings outside the focal element; new piece → every subject mapping it carries stays visible.
- [ ] Bounded redesign → result differs from the recorded baseline on the axes the complaint named?

## Judgment

- Content obligations and action order outrank decorative composition.
- Existing layout conventions outrank a new structural model for a tweak or inserted piece.
- Mobile substance outranks desktop geometry when the two cannot be preserved together.
