# The loop, steps 1-6

1. **Find the plan, settle the workspace, then start the run.** Run `node "${CLAUDE_SKILL_DIR}/scripts/start-run.mjs" --find-only` (`--plan <path>` names one); a failure line on zero or several matches is the question. Settle where the run commits. Read that plan's `Repository:` and `Branch:` lines. Rerun `start-run.mjs --plan <path> --checkout <checkout> --session "${CLAUDE_SESSION_ID}"` to write the marker. Invoking build authorizes commits there and a wave's worktrees beside it; a push or pull request waits for the user's answer to `ship`.
2. **Read the frame, not the plan.** Read `## Goal`, `## Plan basis`, `## Success criterion` and `## Checkpoint`, plus `## Non-goals`, `## Context`, `## Decisions`, `## Visual direction` when present. List tasks with `grep -n '^### Task [0-9]' <plan>`; never open or `@`-reference it, since every turn re-reads it.
3. **Ask the branch what landed.** Run `node "${CLAUDE_SKILL_DIR}/scripts/next-task.mjs" --plan <plan> --root <checkout>`; `Next: none` goes to step 7, `Route:` picks step 5's route. Only a `Plan-task:` commit decides what landed, never memory, so a compaction reruns it first.
4. **Form the block.** Under `Route: unit`, the current and later unlanded tasks in plan order, eight at most, ending before a `Design:` task or an unlanded `Depends on:` outside the block. A current `Design:` task routes, then step 3 repeats. There, an open choice the user would miss stops the run with one question; any other is ruled, recorded in the commit body.
5. **Dispatch.** After the dispatch message, end the turn; each completion notification resumes it. Until all returns are in, never call ScheduleWakeup, ListAgents, Monitor or sleep, or read a worktree or report for progress. A wave lands only after every sibling returned. `Route: unit`: **dispatch the unit**, never build a `Wave:` here. Send each block to the `exo:run-unit` agent, naming plan path, branch, checkout, `<skill>` (`${CLAUDE_SKILL_DIR}` resolved), task numbers. `Route: direct`: a `Next:` line sends its task, a `Wave:` line each task built per the wave worktrees reference in one message, to `exo:build-task` from `../implementer-prompt.md`, which carries `Return: one line`. A `GREEN` line names a diff path this session reads itself, never the report, runs `node "${CLAUDE_SKILL_DIR}/scripts/land-task.mjs" --plan <plan> --task <n> --root <checkout>`, a wave's per that reference's step 3. In a wave, a failed sibling never discards a green task. That reference's step 4 saves each worktree's diff, then removes it. Any other line hands its report path, unread, to a repair delegate: `PLAN DRIFT` to `../drift-repairer-prompt.md`, `BLOCKED` or a failed `Run:` with no cause to `../bug-fixer-prompt.md`, a second failure stops the run `BLOCKED` with both reports and 2-3 options. A land-task refusal other than `PLAN DRIFT` goes to `../bug-fixer-prompt.md`, reruns once; a second stops likewise.
6. **Route the return.** `LANDED` and `GREEN` need nothing. `BUDGET:` means unfinished, whatever its `done` list says: a fresh unit takes the rest from step 3. `BLOCKED all nested dispatch unavailable` ends the turn asking to set `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` to 2 or more. `BLOCKED` with a question runs `node "${CLAUDE_SKILL_DIR}/scripts/resume-plan.mjs" wait` before asking it. Loop to step 3; only a block, failed check or question earns a message. An `exo: context` line: keep working once the task in flight lands.
