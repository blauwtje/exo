# Wave worktrees

A wave, as `run-plan` step 3 forms it, builds each of its tasks in a worktree of its own. The enemy is two delegates editing one checkout, where a build overwrites another's edit before either commits. The overcorrection is a worktree the run leaves behind, holding a stale checkout after the wave lands or is discarded. The run creates, lands and removes every wave worktree itself; a delegate never creates or leaves one.

1. **Create.** When the dispatch tool offers worktree isolation, such as `isolation: "worktree"`, create nothing and dispatch each build with it: a session isolated in its own worktree refuses every command a delegate runs in a sibling folder. Otherwise, for each task run `git worktree add --detach "<root>-task-<n>" HEAD`, where `<root>` is what `git rev-parse --show-toplevel` prints, then the plan's `Worktree setup:` command inside it; `Worktree setup: none` runs nothing. A failed `git worktree add` or setup command discards the wave before any dispatch; the current task then builds alone in the run's checkout and the rest of the run forms no wave.
2. **Brief.** A folder the run made is named as the checkout, with as report directory what `git rev-parse --absolute-git-dir` prints in the run's checkout, because a worktree's own git directory goes when the worktree does. The brief file `next-task.mjs` wrote sits under that same run git directory, outside every wave worktree, so a dispatch to a folder the run made names its path unchanged. An isolated delegate reads nothing outside its worktree, so its dispatch carries the brief's content verbatim, and it gets `Wave:` with the run's `git rev-parse HEAD` and the setup command, and commits with the `Commit:` block its brief holds: the harness may base its worktree on `origin/<default branch>`, and the run cannot enter that worktree to set it up or commit.
3. **Land.** With every report green, run `node "${CLAUDE_SKILL_DIR}/scripts/land-task.mjs" --plan <plan> --task <n> --root "<root>-task-<n>"` for each folder the run made, which runs that task's `Commit:` block there, or take the `Commit:` sha an isolated delegate returned, then on the run branch `git cherry-pick <sha>` for each task in plan order; a folder's sha is what `git -C "<root>-task-<n>" rev-parse HEAD` prints. A cherry-pick that stops on a conflict is undone with `git cherry-pick --abort`, the worktrees are removed, and the turn ends naming the tasks of the conflicting cherry-pick.
4. **Remove.** Run `git worktree remove "<root>-task-<n>"` for each folder the run made, and `git worktree remove` on the path an isolated delegate's result names. A discarded wave adds `--force`, because its edits were never committed and the plan holds the code that rebuilds them. A branch the harness made for an isolated worktree stays and is named in the run's report, because its commit exists only there until the cherry-pick. No turn ends, stops or asks while `git worktree list` still prints a wave worktree this run made.

## Judgment

- A failed `git worktree add` or setup command discards the whole wave, even for tasks whose own worktree would have built cleanly, because a wave that lands short a task is the same divergence a mid-wave failure produces.
- A cherry-pick conflict undoes with `git cherry-pick --abort`, never a manual resolve in the run's checkout, because a resolved conflict there is a commit no task branch holds.
- `git worktree list` printing a leftover wave worktree outranks a green report: the turn stays open until step 4 removes it, so a cleared context never inherits an orphaned checkout.
