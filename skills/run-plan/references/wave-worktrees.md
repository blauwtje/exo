# Wave worktrees

A wave, as `run-plan` step 3 forms it, builds each of its tasks in a worktree of its own. The enemy is two delegates editing one checkout, where a build overwrites another's edit before either commits. The overcorrection is a worktree the run leaves behind, holding a stale checkout after the wave lands or is discarded. The run creates, lands and removes every wave worktree itself; a delegate never creates or leaves one.

1. **Create.** For each task run `git worktree add --detach "<root>-task-<n>" HEAD`, where `<root>` is what `git rev-parse --show-toplevel` prints, then the plan's `Worktree setup:` command and `node "${CLAUDE_SKILL_DIR}/../../lib/scratch-path.mjs"` inside it, which creates its `.exo/` report directory; `Worktree setup: none` runs nothing. Never dispatch a build with the dispatch tool's worktree isolation, such as `isolation: "worktree"`, because an isolated delegate reads nothing outside its worktree, so its brief and report would ride in the run's context. A failed `git worktree add` or setup command discards the wave before any dispatch; the current task then builds alone in the run's checkout and the rest of the run forms no wave. Before builds go out, record `git -C <root> status --porcelain` as this wave's baseline; step 3 checks it again once every report returns, because a build without worktree isolation can still write into the run's checkout by mistake.
2. **Brief.** A folder the run made is named as the checkout, with as report directory its own `.exo/`, because a delegate writes nothing outside its own worktree. The brief file `next-task.mjs` wrote sits under the run's checkout's `.exo/`, outside every wave worktree, so each dispatch names its path unchanged.
3. **Land.** First run `git -C <root> status --porcelain` again and compare it with step 1's baseline: a path it lists now that step 1 did not (`.exo/` never shows, excluded by `lib/scratch-exclude.mjs`) means a report or a build wrote into the run's checkout instead of its own worktree; stop, show the listed paths, land nothing from this wave, go to step 4, which force-removes it as a discarded wave, and end the turn naming those paths. With every report green and the checkout unchanged, run `node "${CLAUDE_SKILL_DIR}/scripts/land-task.mjs" --plan <plan> --task <n> --root "<root>-task-<n>"` for each folder the run made, which runs that task's `Commit:` block there, then on the run branch `git cherry-pick <sha>` for each task in plan order; a folder's sha is what `git -C "<root>-task-<n>" rev-parse HEAD` prints. A cherry-pick that stops on a conflict is undone with `git cherry-pick --abort`, the worktrees are removed, and the turn ends naming the tasks of the conflicting cherry-pick.
4. **Remove.** First copy each folder's `.exo/implementer-<n>.md` into the run's checkout's `.exo/`, because the branch review reads every build report there and a worktree's `.exo/` goes with it. Then run `git worktree remove "<root>-task-<n>"` for each folder the run made. A discarded wave adds `--force`, because its edits were never committed and the plan holds the code that rebuilds them. No turn ends, stops or asks while `git worktree list` still prints a wave worktree this run made.

## Judgment

- A failed `git worktree add` or setup command discards the whole wave, even for tasks whose own worktree would have built cleanly, because a wave that lands short a task is the same divergence a mid-wave failure produces.
- A cherry-pick conflict undoes with `git cherry-pick --abort`, never a manual resolve in the run's checkout, because a resolved conflict there is a commit no task branch holds.
- `git worktree list` printing a leftover wave worktree outranks a green report: the turn stays open until step 4 removes it, so a cleared context never inherits an orphaned checkout.
- A path in the run's checkout's status after the wave that step 1's baseline did not list outranks every green report: the wave lands nothing, even when every task passed its `Run:`.
